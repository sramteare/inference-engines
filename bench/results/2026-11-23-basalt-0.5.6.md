# Basalt 0.5.6 against our serving builds, on 256 GB RAM (2026-11-23)

Upstream Basalt is at 0.5.6. Our two serving builds were behind it:
- **Qwen:** 0.4.1, `~/dev/basalt-src`.
- **DeepSeek:** 0.5.0 + PR #481, `~/dev/basalt-ds41-serve`.

This file compares each against 0.5.6 on the same machine, on the same day.

## Hardware

`basalt-bench --hardware`, plus `dmidecode`.

- CPU: AMD Threadripper PRO 9955WX, 16 cores.
- GPU: RTX PRO 6000 Blackwell Max-Q, power limit 300 W, PCIe 5.0 x16, host-to-device 57.0 GB/s.
- **RAM: 2 x 128 GB DDR5 at 6400 MT/s, on channels C and D only.** The other 6 slots are empty.
  - 246 GiB usable.
  - **75.9 GB/s read.** The earlier 4 x 32 GB at 4800 on 4 channels read about 90 GB/s.

- **The conflict:** one, in `src/kernels/cuda/iq_kernels.cu`. Upstream added MXFP8 (type 46); #481 adds MXFP4 (39) and IQ3_S down (21).

## Qwen3.8-Flash-Next (UD-Q4_K_XL)

### Speed

`basalt-bench --seed 1 -t conv,struct,prose -p 16384,65536 -- --kv fp16 --max-context 262144 --vram-reserve-mib 3772 --resident-experts --vision`

These are the serving flags. Each run is a fresh engine. There were 12 runs, alternating builds (ABBA BAAB ABBA), with 60 s of cool-down before runs 5-12. Figures are mean +- stddev in tok/s, n = 6 per build.

| Test | 0.4.1 | 0.5.6 | Change |
|---|---|---|---|
| tg conv | 295.7 +- 8.6 | 292.2 +- 5.7 | -1.2% |
| tg struct | 495.0 +- 14.2 | 485.8 +- 10.5 | -1.9% |
| tg prose | 248.5 +- 5.9 | 242.2 +- 4.8 | -2.5% |
| pp16384 | 7508 +- 157 | 7385 +- 139 | -1.6% |
| pp65536 | 7970 +- 227 | 7852 +- 157 | -1.5% |

- **Same drafting:** draft acceptance (69.8 / 97.7 / 60.1%) and draft length were identical in every run.
- **Borderline, not clearly noise:** all five tests are 1.2-2.5% slower on 0.5.6. The largest, prose, is a gap of 6.3 tok/s against a standard error of about 3.1, so about 2 standard errors. Most of the gap comes from 2 of the 6 back-to-back pairs, and 0.4.1 itself varied by up to 6% between runs. A small real slowdown (about 2%) can't be ruled out.
- **Upstream:** it reports 0.5.6 within 1% of 0.5.5 on this model.

**Not tracked down:** if the gap is real, the likely sources are these commits:
- 0399fdd and 21c685a: Q8_0 products of 2-7 columns on new kernels, which affect every drafted window.
- 1f4813f, fdf1e22 and 0961aa1: the router, hyper-connection and norm kernels moved into shared code.
- 871c498: router logits for launches of 64 tokens or more, which affects prompts.

### Two conversations at once, 1 slot (fp16) against 2 slots (int8 KV)

`partest.py LABEL 3000 4 2000 long` sends two conversations of about 110K tokens each. Each has 4 turns of long code output, and both send at the same time. Each test has its own server on :8000 with the serving config. The 2-slot runs add `kv: int8, parallel: 2, slot-full-context: true`.

| Build, config | Wall | Output | Aggregate | Mean later-turn request |
|---|---|---|---|---|
| 0.5.6, 1 slot fp16 | 74.1 s | 12,338 | 166.5 tok/s | 11.1 s |
| 0.5.6, 2 slots int8 | 71.9 s | 11,890 | 165.4 tok/s | **7.9 s** |
| 0.4.1, 1 slot fp16 | 76.7 s | 12,485 | 162.8 tok/s | 11.7 s |
| 0.4.1, 2 slots int8 | 67.9 s | 10,590 | 156.0 tok/s | **6.6 s** |

- **Shorter waits, about the same total:** two slots cut the wait for later turns by 29% on 0.5.6 and 44% on 0.4.1. Total throughput is the same on 0.5.6 (165.4 vs 166.5) and 4% lower on 0.4.1 (156.0 vs 162.8). The 2-slot runs also wrote fewer tokens (10,590-11,890 vs 12,338-12,485), so the per-request times are not exactly like for like. One run each; this matches the 2026-11-22 test.
- **While both slots generate:** each runs at about 190-200 tok/s, about 380-400 together, and 85-91% of drafts are accepted.
- **Basalt still needs int8 KV for batch slots in 0.5.6.** Its own precision table rates int8 KV lossless for Flash-Next: dKLD +0.0000 [-0.0010, +0.0010], top-1 +0.15.

## DeepSeek-V4.1-Flash (UD-Q2_K_XL.vision.basalt)

### What the pack holds and where it is served from

The section table of the 320.7 GiB pack (344 GB):

| Section | Size | Served from |
|---|---|---|
| experts (routed) | 178.0 GiB | VRAM + RAM; none from the file now |
| engram | 125.9 GiB | the SSD, by design: O_DIRECT row reads with a small row cache, requested a step ahead |
| gguf (attention, shared expert, norms, head) | 7.9 GiB | VRAM |
| dspark/gguf (drafter) | 7.4 GiB | VRAM |
| vision/mmproj | 0.9 GiB | VRAM (`vision: dynamic` when serving). Not free at rest on DeepSeek: about one expert per layer less GPU cache (159 vs 160 card experts per layer, measured in PR #15); the serve log shows `vision=gpu0` |
| dense, tokenizer, meta | 0.6 GiB | |

**Expert placement:**
- **0.5.6, default flags:** start line `expert homes of 384 per layer: main card 134, second card 0, RAM 250, file 0`, with a VRAM expert tier of 62.12 GiB and 15 CPU pool workers.
- **On the old 128 GB (PR #481's run):** card 145, RAM 159, SSD 80 per layer. That means 37.1 GiB of experts were read from the SSD.

### Speed

`basalt-bench --seed 1 -t conv,struct,prose -p 16384,65536 -- --max-context 524288 --vram-reserve-mib 3772 --vision`

These are the serving flags. Runs alternated old, new, new, old with 30 s between them. Figures are the mean of 2 runs, in tok/s.

| Test | Old (0.5.0 + #481) | 0.5.6 + #481 | Change |
|---|---|---|---|
| tg conv | 104 (99, 109) | 111 (110, 112) | +7% |
| tg struct | 205.5 (205, 206) | 204 (208, 200) | -1% |
| tg prose | 96.5 (96, 97) | 93.5 (95, 92) | -3% |
| pp16384 | 2386 (2378, 2394) | 2354 (2380, 2328) | -1% |
| pp65536 | 2932 (2905, 2959) | 2897 (2942, 2851) | -1% |

- **Same speed on both builds.** Run-to-run spread is about 5%. The conv gap follows draft acceptance, which varied from 69% to 77% between runs.
- **The RAM upgrade gives a large gain over PR #481's earlier run on 128 GB:** conv 69, struct 149, prose 74, pp16384 1933. The flags and pack differed, so the figures only point in a direction. The likeliest main cause is the SSD expert tier going away (80 experts per layer then, 0 now), but nothing here isolates it.
